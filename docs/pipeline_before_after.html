VoiceStudio dubbing pipeline

What happens at every stage, before and after the CSV import feature. Hindi → Telugu, 12:40 source, 168 lines, 6 speakers. Every number here was measured on job fno0wbe7 and its predecessors, 20 Aug 2026.
THE SIX STAGES (unchanged in both modes) Upload → Prepare → Transcribe → Edit → Generate → Export ^^^^^^^^^^^^^^^^^^ this is the only part CSV import replaces

1. The short answer

StageBefore CSV import After CSV import
Upload Video goes to the server, a job row is created Identical
Prepare ffmpeg extracts audio; Demucs splits it into vocals.wav and no_vocals.wav Identical — and still required. Voice cloning needs vocals.wav
Transcribe ASR + diarization + Chirp word timings + gap filling + onset snapping + line reshaping. 7 models decide your timeline. All of it skipped. Your CSV is the timeline. Voice clones are cut immediately
Translate An LLM translates each line and tries to fit it to the slot Skipped. Your translation CSV is used verbatim
Edit You fix mistakes by hand Identical (usually nothing to fix)
Generate Voice cloning → TTS → wrong-language check → place → mix Identical, except placement is forced to strict_slot
Export Mux video with the dub track Identical
The one sentence version. CSV import removes every model that was guessing what was said, who said it, and when — and leaves every model that produces the dubbed voice. Stages 3 and 4 become file reads. Stage 5 is untouched.

2. Before CSV import — what ran inside "Transcribe"

This single button hid seven decisions. Each one could be wrong, and each error fed the next.

3a. Speech recognition

gemini-3.7-flash via an OpenAI-compatible proxy transcribes the Hindi. Produces the words, but its timestamps drift — measured up to 157s of drift on a 12-minute file in published tests, which is why its timings are never used directly.

3b. Speaker diarization

pyannote decides how many people are speaking and labels each line. Capped at 8 speakers (OMNIVOICE_DIAR_MAX_SPEAKERS). Its known failure is collapsing several voices into one — one job had 75% of all speech assigned to a single speaker until it was forced to split.

3c. Word timings from Google Chirp 2

The audio is sent to Google Speech-to-Text v2 (chirp_2, us-central1, enableWordTimeOffsets) purely for when each word was spoken. Each line is then matched onto that word stream and takes those times.

Measured problem: Chirp 2's word onsets run 90–150 ms early on average, with a tail to −4.3 s. In a 7-language benchmark against constructed ground truth it placed only 0–31% of line starts inside the acceptable window.

3d. Gap filling

Speech with no line over it is treated as missing dialogue, so extra lines are invented to cover it. One historic bug spread 24 words evenly across a 0.56 s gap.

3e. Line reshaping

Lines that look too sparse are split, slivers too short to speak are absorbed into neighbours, repeated junk text is cleaned. Your line boundaries change here.

3f. Onset snapping

Line starts are nudged onto detected speech onsets, up to 0.6 s (SNAP_MAX_S) or 1.5 s in the aligner (MAX_SNAP_S).

3g. Quality scoring

A "well placed" percentage is computed — but on the merged blocks, before the speaker split turns them into the lines that actually get rendered. On one job that reported 88.5% on 26 blocks while the 31 rendered lines scored 53.3%. The number described a timeline that was never used.

4. Translation

An LLM translates line by line and is asked to keep the result short enough to fit. Character count is a weak proxy for duration — it explains under 10% of the real variance.

3. After CSV import — what replaces it

3. Import Transcript CSV REPLACES 3a–3g

POST /dub/import/transcript/{job_id} with line_id,speaker,start,end,source_text

Each row becomes one segment. Nothing is recalculated: no ASR, no diarization, no Chirp call, no gap filling, no reshaping, no snapping. Speaker labels SPK1..SPK6 map to Speaker 1..6. The job is stamped timing_source = manual-csv-v1.

Then the file is validated and refused outright if it would produce a broken dub — duplicate line_id, more than 8 speakers, a speaker with under 3 s of speech, end ≤ start, an ellipsis in the source text, bad UTF-8. On refusal nothing on the job changes.

Finally the six voice clones are cut from vocals.wav using each speaker's own lines, and the import re-reads the saved row to prove every value survived.

4. Import Translation CSV REPLACES translation

POST /dub/import/translation/{job_id} with line_id,start,end,target_text,notes

Joined on line_id — not on row order, so a file that has drifted by one row is detected instead of silently pairing the wrong text with the wrong line. Sets the target text only; start, end and source text are never touched.

What is now bypassed by construction

The Chirp timing, onset snapping and gap filling code has no call site in the render path at all — it only ever ran from the Transcribe endpoints. Importing a CSV skips those endpoints, so those stages cannot run even if they are switched on.

4. Stage 5 "Generate" — identical in both modes

This is where the dub is actually produced, and CSV import changes only one thing in it.

for each line: 1 reference cut a few seconds of that speaker's real HINDI voice from vocals.wav, with the Hindi words in it [voice cloning input] 2 synthesis the engine generates, as ONE continuous stream: [ Hindi reference words ] -> [ your Telugu line ] and only the Telugu region is kept 3 check the produced clip is transcribed. Is it actually Telugu? NO -> throw it away and generate again (this is a "re-render") YES -> keep it 4 front remove leading near-silence so the first syllable lands on your start 5 place put the clip at exactly your start value [strict_slot] 6 mix lay it over no_vocals.wav (music and effects kept)
Why re-rendering happens even though you supplied everything. Step 2 is the reason. The engine speaks the Hindi reference and your Telugu as one breath, and we cut where the Telugu should begin. When it is still finishing the Hindi, the kept clip contains Hindi audio — despite the text asked for being pure Telugu. Step 3 catches that and regenerates.

This has nothing to do with your CSV. It is the voice cloner failing and being caught. It is also exactly the "Hindi playing before the Telugu line" problem — and the check fixes it by regenerating, never by deleting words (measured: cut_s: 0.0).

The one change CSV import makes here: placement is forced to strict_slot with slot_fit = off. strict_slot does place_at = start. The other modes (smart_fit, stretch_video) lay each clip on their own running cursor and re-time the video, which would move your timestamps.

7. Practical notes

  • Prepare still has to run before importing. The import cuts voice references from vocals.wav, which does not exist until separation finishes. Importing before that returns 404 Job not found.
  • Do not press Translate All after importing — it would overwrite your imported Telugu.
  • Do not let a transcription finish alongside an import. The two can race, and the browser can end up showing a merged timeline (168 of yours plus the AI's). A hard refresh reloads the correct set from the server.
  • Set Default Track to Telugu before exporting, or the MP4 plays Hindi by default even though the Telugu track is present.
  • Revert: .\revert_csvimport.ps1 -Status, then -Level ui | router | all.
