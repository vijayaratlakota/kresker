VoiceStudio — Cross-Account Migration Runbook

Moving the whole 115 GB GPU pipeline to a different AWS account, bit-for-bit, with every connection intact
The short answer: yes, and it is the easy kind of migration. You do not rebuild anything. You take one disk image of the machine as it stands today, hand it to the new account, and boot it. Because the image is a byte-level copy of the 150 GiB root volume, the patched backend, the tuned settings, the 20 GB of models, the Docker container with its baked-in environment, the Google credentials and the Gemini proxy service all arrive already configured. Nothing is reinstalled, so nothing can drift. Expect 2–3 hours of work and one long unattended copy.
One thing has a lead time of days, not hours. A new AWS account usually cannot launch a GPU instance at all — the quota starts at zero and only a support ticket raises it. Read section 4 and raise that ticket now, while the current account still has credits. Everything else in this document can be done in an afternoon.

Three things follow from that diagram, and all three were confirmed live today:

  • The proxy address is host-independent. 172.17.0.1 is the Docker bridge gateway, which is the same on every Docker host with a default bridge. It contains no public IP, no hostname and no account ID, so it needs no edit after migration. Verified answering HTTP 200 from inside the container.
  • The proxy does no authentication of its own. Its source says the api_key VoiceStudio sends is ignored, because authentication to Google happens with an OAuth bearer token minted from the ADC file. Tested: a request with no Authorization header returns 200, and so does one with a deliberately wrong key. That is why the encrypted key in the settings database turns out to be a 6-character placeholder, and why section 9's trap is survivable.
  • The Google credential is a user refresh token, not a service account. type: authorized_user, with quota_project_id = project-35cd3678-bfdd-451b-bcc. It minted a fresh access token during this audit (expiry 18:44 UTC) and Speech-to-Text v2 answered 200 in us, eu and us-central1. The proxy listed eight Gemini models. Everything on the Google side is alive right now.

3. Why a disk image, and what the alternatives silently lose

There are three ways to move this workload. They are not equally safe, and the difference is not effort — it is how many chances there are for something to end up subtly different.

MethodWhat it copiesWhat it does not copyVerdict
A. AMI share + copy
RECOMMENDED		Every written block of the 150 GiB root volume: OS, driver, Docker, the image, the container's writable layer, the named volume, the systemd unit, the credentials, the jobsOnly the four AWS wrappers in section 6, and the public IPUse this. There is no reinstall step, so there is no opportunity for a version to drift. The pipeline arrives byte-identical and section 7 proves it.
B. Container export + host filesThe container as a flattened image, plus the volume and the host bind directories as tar filesThe container's identity (see section 9), the driver, the toolkit, the systemd unit unless you copy it by hand, the exact Docker versionWorkable, documented in section 10, but every item in the middle column is a thing you must remember. Keep as insurance only.
C. Rebuild from Docker Hub + re-apply patchesThe stock 0.4.2 applicationAll of it. The 124,556 added and 48 modified paths, the tuned module defaults, the model cache, the settings databaseDo not. This is not a migration, it is redoing the work. The tag :latest may also no longer be the 12 Aug build.
The trap in method A that costs people their data. A shared AMI stays owned by the source account. The target account can launch from it, but it does not own it. On the day the old account is closed or its resources are deleted, that AMI and its backing snapshot disappear — and any instance launched from it can no longer be re-launched from scratch. The target account must copy the AMI into itself (aws ec2 copy-image), which creates a brand-new AMI and a brand-new snapshot that the target account owns outright. Step 5.7 does this, and step 5.11 is where you confirm the copy exists before you let go of the old account. Do not skip either.
A detail about permissions that is easy to get wrong. To merely launch from a shared AMI, sharing the AMI's launch permission is enough — AWS grants the launch access to the backing snapshot on your behalf. But to copy the AMI, the target account also needs read access to the backing snapshot itself. Since copying is exactly what you must do, step 5.5 shares both the AMI and its snapshot. Sharing both is the safe superset and costs one extra command. (Sources: AWS — Share an AMI with specific AWS accounts, How to share an AMI across AWS accounts. Content was rephrased for compliance with licensing restrictions.)

4. Do these three things now, before credits run out

The migration itself is an afternoon. These three items are not, and two of them get harder the longer you leave them.

4.1 Raise the GPU quota in the target account — this has a lead time of days URGENT

The source account's quota for Running On-Demand G and VT instances is 4 vCPUs — exactly one g4dn.xlarge, which is 4 vCPUs. A newly created AWS account very often has this quota set to 0, which means run-instances fails outright with VcpuLimitExceeded no matter how correct everything else is. Raising it requires a Service Quotas request that a human at AWS reviews. That review has historically taken anywhere from a few hours to several business days, and brand-new accounts with no billing history are the slowest cases.

In the target account, check and request:

# the quota code for "Running On-Demand G and VT instances" is L-DB2E81BA
aws service-quotas get-service-quota --service-code ec2 \
    --quota-code L-DB2E81BA --region ap-south-1 --profile NEWACCT

# if the Value is below 4, request 8 (headroom for one instance plus a rehearsal)
aws service-quotas request-service-quota-increase --service-code ec2 \
    --quota-code L-DB2E81BA --desired-value 8 --region ap-south-1 --profile NEWACCT

Ask for 8, not 4. Eight vCPUs lets you run the new instance while the old one is still up, which is what makes the rehearsal in section 11 and the side-by-side comparison in section 7 possible. Requesting exactly 4 forces you to shut down the working machine before you have proved the new one, which is the opposite of how you want to do this.

Raise this ticket while the source account still works. If credits run out first you will be trying to get a GPU quota approved in a new account while your only working copy of the pipeline is on an account you can no longer start. There is no technical reason to wait.

4.3 Confirm the Google side has its own runway

The pipeline's dependency on Google is separate from AWS and will not be fixed by moving AWS accounts. Verified alive today, but check all three before you rely on them:

  • Vertex AI credits/billing on project project-35cd3678-bfdd-451b-bcc. The proxy's own header comment notes this project is the one with working credits. If those credits expire, transcription and translation stop — on any AWS account.
  • The refresh token. It is a user OAuth credential (type: authorized_user), not a service account. Google can invalidate a refresh token if it goes unused for an extended period, if the owning account's password changes, or if access is revoked. It works today. If you want to remove that whole class of risk before migrating, replace it with a service-account key: create one in the same project, grant it Vertex AI User and Cloud Speech Client, and drop the JSON in at both /home/ubuntu/gcp_adc.json and the container's /root/gcp_adc.json. Both consumers use google.auth.default(), which accepts either type without a code change. Do it on the old box first and confirm a render still works, then migrate.
  • Speech-to-Text v2 access in the us and eu multi-regions, which is where chirp_3 is served from. Confirmed 200 today.

5. The runbook, step by step

Throughout: OLD means the current account 959689755912 with CLI profile videotrans, and NEW means the target account with a profile you will call NEWACCT. Replace NEW_ACCOUNT_ID with the 12-digit target account number. Every command that changes something is marked.

Part A — on the OLD account

5.1 Confirm the box is genuinely idle SAFE

An image taken mid-render captures half-written WAV files and a SQLite database mid-transaction. Not fatal for the pipeline code, but it makes the section 7 verification ambiguous, and ambiguity is what you are trying to avoid.

Do not trust a process count alone. The render runs inside the uvicorn process, so ps | grep speaker_clone reports zero while a job is very much in flight. This nearly caused a mid-render image on 2026-08-23. The reliable signals are GPU utilisation and whether job_events is still growing: 
.\rsh.ps1 -Script _bk_watch.sh    # 5 samples over 40s: gpu, job_events count, log size
Idle means GPU at 0% and both counters frozen across all five samples. If you see seg_<lang>_cNNN.wav filenames climbing, a render is running — wait for bench[generate] total=… in the log, which is the completion marker.

5.2 Create the AMI, without stopping the instance CHANGES THINGS

Because an EBS snapshot is point-in-time, an idle box does not need to be stopped. This is the better trade: no downtime, no IP change, and nothing lost from a browser tab holding a translation.

aws ec2 create-image \
  --instance-id i-041b48c591cb86e19 --no-reboot \
  --name "voicestudio-golden-20260823" \
  --description "VoiceStudio 0.4.2 verified-good pipeline. chirp_3 + fa_then_chirp + MMS stars + band gate; bridge OFF, head-lang OFF. Full 150GiB disk. Taken while idle." \
  --tag-specifications 'ResourceType=image,Tags=[{Key=Name,Value=voicestudio-golden-20260823},{Key=Purpose,Value=backup-and-migration}]' \
  --profile videotrans --region ap-south-1

Then verify the instance really was untouched — --no-reboot should leave RestartCount at 0 and the container's StartedAt unchanged:

.\rsh.ps1 -Script _mig_nochange.sh    # five MD5s, byte counts, marker count, restart count
.\backup_status.ps1 -Watch            # poll the snapshot to completion
Measured timing, replacing an earlier estimate. This document originally guessed 20–60 minutes. The real first snapshot of this 115 GB volume ran at a steady 1.25% per minute (5% at 7.8 min, 14% at 15 min), which is about 80 minutes end to end. Budget an hour and a half. Subsequent snapshots are incremental and far quicker. The instance is fully usable throughout — you can dub while it copies.

Stopping the instance first is still the textbook approach and gives an application-consistent image rather than a crash-consistent one. It costs a stop/start cycle and a new public IP. With the box verified idle by the signals in 5.1 there is nothing in flight to be inconsistent about, so --no-reboot is the better choice. If you ever image mid-render, stop the instance instead.

5.3 Nothing to restart SAFE

With --no-reboot the box never went down, so there is no restart, no new IP and no aws_lock_ip.ps1 re-run. Confirmed on 2026-08-23: instance still running at the same address, container RestartCount 0, uvicorn still the process started at 17:16:05, and all five module MD5s golden after imaging.

If you did stop the instance in 5.2, this is where you bring it back:

.\start_box.ps1                    # writes the new IP into _vs_ip.txt
.\aws_lock_ip.ps1 -Apply           # re-lock the security group to this laptop's IP
.\rsh.ps1 -Script _ready_check.sh  # markers 5, speech_rate 13073, chirp_3, fa_then_chirp

5.4 Record the fingerprints you will verify against SAFE

These are already in the handbook, but capture them again from the live box so you are comparing against the state you actually imaged, not a remembered one:

.\rsh.ps1 -Script _mig_facts.sh > _mig_facts_before.txt

5.5 Share the AMI and its snapshot with the new account CHANGES THINGS

# the AMI itself - lets NEW launch from it
aws ec2 modify-image-attribute --image-id ami-NEWID \
  --launch-permission "Add=[{UserId=NEW_ACCOUNT_ID}]" \
  --profile videotrans --region ap-south-1

# the backing snapshot - lets NEW *copy* it, which is the part that matters
aws ec2 modify-snapshot-attribute --snapshot-id snap-XXXX \
  --attribute createVolumePermission --operation-type add --user-ids NEW_ACCOUNT_ID \
  --profile videotrans --region ap-south-1

Confirm both took:

aws ec2 describe-image-attribute --image-id ami-NEWID --attribute launchPermission \
  --profile videotrans --region ap-south-1
aws ec2 describe-snapshot-attribute --snapshot-id snap-XXXX --attribute createVolumePermission \
  --profile videotrans --region ap-south-1

There is no KMS step, because the volume is unencrypted. If you ever repeat this with an encrypted volume, you would also have to share the customer-managed key and add the target account to its key policy.

Part B — on the NEW account

The Owner will still read 959689755912. That is expected and is exactly why the next step exists. The quota value must be at least 4.

5.7 Copy the AMI so the new account owns it CHANGES THINGS · DO NOT SKIP

aws ec2 copy-image \
  --source-image-id ami-NEWID --source-region ap-south-1 --region ap-south-1 \
  --name "voicestudio-golden-20260823-owned" \
  --description "Owned copy. Survives closure of account 959689755912." \
  --profile NEWACCT

aws ec2 wait image-available --image-ids ami-OWNEDID --profile NEWACCT --region ap-south-1

This is another 20–60 minute wait; it creates a fresh snapshot in the new account. When it finishes, describe-images --owners self in the new account must list it. That listing is your proof that the pipeline no longer depends on the old account existing.

Copying to a different region works identically — set --region to the destination and --source-region to ap-south-1. Only do that if you actually want to move region; it makes the copy slower and changes your latency to Google's us/eu Speech endpoints.

5.8 Create the security group CHANGES THINGS

MYIP=$(curl -s https://checkip.amazonaws.com)   # your laptop's current public address

aws ec2 create-security-group --group-name videotrans-sg \
  --description "Video translator GPU access" --profile NEWACCT --region ap-south-1

for P in 22 3000 3900; do
  aws ec2 authorize-security-group-ingress --group-id sg-NEW \
    --ip-permissions "IpProtocol=tcp,FromPort=$P,ToPort=$P,IpRanges=[{CidrIp=$MYIP/32,Description=locked}]" \
    --profile NEWACCT --region ap-south-1
done
Do not open port 8900. The Gemini proxy listens on 0.0.0.0:8900, not on loopback, and it performs no authentication of its own. The only thing keeping it private is that the security group has no rule for that port. Anyone who could reach 8900 could spend your Vertex AI credits. The same applies to 3900: the app accepts no credentials and returns 200 to anyone who can reach it, which is why aws_lock_ip.ps1 exists. Keep both restricted to a single /32.

5.9 Create the IAM role and instance profile CHANGES THINGS

Nothing on the box calls an AWS API today — verified: no module under /app/backend imports boto3, even though the library is installed. So this role is currently decoration. Recreate it anyway, with the same name, so that aws_lock_ip.ps1 and the sibling grant scripts keep working unchanged, and so the option of using Amazon Translate or Bedrock later is still there.

# trust policy
cat > trust.json <<'EOF'
{"Version":"2012-10-17","Statement":[{"Effect":"Allow",
 "Principal":{"Service":"ec2.amazonaws.com"},"Action":"sts:AssumeRole"}]}
EOF

aws iam create-role --role-name OmniVoiceTranslateRole \
  --assume-role-policy-document file://trust.json --profile NEWACCT

7.3 Tier 3 — the end-to-end control. This is the check that actually catches things.

The offline bench cannot catch wiring faults, and that has already bitten this project once. The English snap-bridge patch passed a 14-condition bench perfectly — 0 of 480 non-English line starts moved — while in reality it had silently disabled the onset snap for every language, because it called a variable that did not exist at that call site and an existing try/except swallowed the NameError. The bench missed it because it calls functions directly instead of going through the pipeline. What caught it was re-rendering a real Hindi video and noticing 35 of 139 start times had moved.

So: re-render a known job on the new box and compare per-line timings, not just the audio.

The strongest available control is faprim01, the reference job, which is in the image at /root/.omnivoice/dub_jobs/faprim01 (434 MB). It has been reproduced bit-identically twice and its scores are known:

Measure on faprim01Expected
Well-placed lines75.5%
Badly placed lines12.2%
Line starts and ends139 of 139 bit-identical to the pre-migration run

Two cautions when re-rendering, both learned the hard way:

  • The render reuses existing seg_<lang>_*.wav clips, so a re-render can ship stale audio and tell you nothing. Park those clips first. Keep seg_ref_* and voice_speaker_* — those are the per-line voice reference clips the cloning depends on.
  • One GPU arm at a time. Contention has silently corrupted a measurement before. Do not run the new box's verification render while the old box is also rendering.

Finally, the check that needs no tooling: dub one short video and listen. The three things the verified-good state was signed off on by ear were timing is correct, voice cloning is correct, and no Hindi audio in front of Telugu lines. If all three hold, the migration is done.

7.4 Will the pipeline change? Will the output video change?

These are two different questions with two different answers, and conflating them causes needless worry. Both were checked on the box rather than reasoned about.

The pipeline does not change. This is provable, not a hope.

An AMI is a block-level copy of the volume. The bytes that arrive are the bytes that left, and section 7.1 measures exactly that. Every input to the pipeline's behaviour is carried:

Determinant of behaviourValue, carried in the imageCould it differ after migration?
The seven tuned modulesfive MD5s + two byte counts + marker count 5No — byte-identical, and 7.1 proves it
Module defaults (the settings)chirp_3, fa_then_chirp, stars on, band gate on, bridge off, head-lang offNo — they are literals in the files above
Provider routingbase_url http://172.17.0.1:8900/v1, stored in plaintextNo — the address is the Docker bridge gateway, identical on any host
GPUTesla T4, compute capability 7.5No, provided you launch g4dn.xlarge. See the warning below.
Driver / CUDA / cuDNN / torch580.126.09 · cu128 · cudnn 91002 · torch 2.8.0No — all four live on the imaged disk, none are installed at boot
Numerics flagsTF32 matmul off, cudnn.benchmark offNo — and both being off is what makes local stages reproducible run to run
Model weights15 cached repos, each pinned to a specific revision hash in refs/mainNo, because the cache is carried rather than re-downloaded. This is why section 14 says do not delete models you have not proven unused.
The one way you could change the numerics: launching a different instance type. A g5.xlarge has an A10G at compute capability 8.6, not a T4 at 7.5. Different kernels, different accumulation order, subtly different local model output. It would probably sound fine, but it would no longer be the state that was signed off. Launch g4dn.xlarge. The second way is letting a model re-download: if the cache were rebuilt, Hugging Face could serve a newer revision than the pinned hashes above.

The output video: as reproducible as it is today, and no less

Three stages of the pipeline are remote, and remote generation is not bit-exact. Verified from the code:

  • Translation runs through Gemini with temperature=0.2 pinned by dub_translate.py (the proxy's own default is 0.3, and the reflect pass uses 0.1 or 0.4). Any temperature above zero means sampling, which means the wording of a line can differ between two runs.
  • Transcription uses gemini-3.7-flash through the shim. Google can change what sits behind that label at any time.
  • Chirp 3 word timings come from Speech-to-Text v2. chirp_3 is a label, not a pinned version.

The local stages, by contrast, are deterministic: MMS forced alignment runs a fixed model in .eval() mode, the TTS path calls torch.manual_seed(used_seed) when the voice profile carries a seed, and the ffmpeg mux is deterministic.

The point that resolves the worry: none of that variability is caused by migration. Two fresh renders of the same video on the current box, today, can differ in translation wording for exactly the same reason. Moving AWS accounts does not touch Google, the models, the temperatures or the code. It changes who pays the EC2 bill. What governs quality — timing placement, voice cloning, and no source-language audio in front of a line — lives entirely in the seven files whose fingerprints you verified. Those are byte-identical, so quality is unchanged.

And a caching detail that makes the verification in 7.3 genuinely fair

Each job directory caches its remote results, which is why the reference job reproduced bit-identically twice:

Cached artefactWhat it means for a re-render
chirp_words_cache.jsonThe Chirp word timings for that job, stored on disk (CACHE_NAME in chirp_wire.py). Present in 10 of the 17 job directories, including faprim01. A re-render does not re-ask Google.
pre_retime_segments.jsonThe segments before retiming.
dub_history.tracksThe translated lines, one entry per recent job. A re-render reuses them rather than re-translating.
seg_<lang>_*.wavThe rendered per-line audio — also reused, which is the trap: park these before re-rendering or you will be shipping and measuring stale audio.

So re-rendering faprim01 on the migrated box exercises the local pipeline against frozen remote inputs. If 139 of 139 line starts match, that is a clean measurement of the part that migration could conceivably have affected. A brand-new video is a weaker test, because you cannot separate a migration fault from ordinary sampling variation.

9. The machine-identity trap in the settings store

This is the subtlest thing in the migration, and it is worth a page because it is the kind of fault that produces a confusing symptom rather than a clean error.

9.1 What the code does

The provider settings live in the settings table of /root/.omnivoice/omnivoice.db. Eight rows, of which three are plaintext and readable, and two are Fernet ciphertext:

_secret_key_salt              <16 random bytes, base64>
llm.active_provider           custom
llm.base_url.custom           http://172.17.0.1:8900/v1
llm.model.custom              gemini-3.1-pro-preview
asr.openai_compat.base_url    http://172.17.0.1:8900/v1
asr.openai_compat.model       gemini-3.7-flash
secret.llm_key.custom         <Fernet ciphertext>
secret.asr_openai_compat_key  <Fernet ciphertext>

The Fernet key is not stored anywhere. It is derived on demand by services/_secret_key.derive_fernet_key(), which runs scrypt (n=2^14, r=8, p=1) over the OS machine identifier, salted with that _secret_key_salt row. The module's own docstring is explicit about the consequence: copying the database to another machine produces a key that cannot decrypt the existing rows, and the caller logs a warning and falls back to environment variables.

9.2 What that resolves to on this box, specifically

Here is the part you would not guess. Inside the container, /etc/machine-id exists but is empty. So the Linux branch of _read_machine_id() finds nothing usable and drops through to the documented last resort: hostname + "::" + user. The container's hostname is 9276383fe31e — which is Docker's short container id — and the user is root. The audit log confirms it, verbatim: "Could not read OS machine-id; falling back to hostname+user."

The encryption key for the settings store is therefore a function of the container's id. Which gives a clean rule:

ScenarioContainer hostnameResult
Method A: AMI copy. The same container object is carried inside /var/lib/docker and simply restarts.9276383fe31e (unchanged)decrypts fine — nothing to do
Restarting or stopping the container, or rebooting the host9276383fe31e (unchanged)decrypts fine — this is why it has survived every stop/start so far
Method B, or any docker run that creates a new containera new random iddecryption fails — the two keys fall back to env, which is unset

9.3 Why this is survivable, and the one-word fix if it bites

Two mitigations, and it is worth knowing both:

  • The secrets barely matter. Both decrypt to a 6-character placeholder, and the proxy ignores the API key entirely — its source says so, and a request with a deliberately wrong key returns 200. The base URL, which is the setting that actually routes the traffic, is stored in plaintext and migrates regardless.
  • If you ever do recreate the container, pin its hostname. Add --hostname 9276383fe31e to the docker run, and the derived key comes out identical, and the existing ciphertext decrypts. This is the single most useful line in section 10.

And if it does fail, the symptom and the repair are both mild: the app logs an InvalidToken warning, and you re-enter the two keys once in the Settings page (any value will do, since the proxy ignores them). It is a five-minute annoyance, not a data loss — but only if you know to look for it, which is why it has a section.

The five things this method loses if you are not careful, all of which method A gets for free:
  1. The container's identity. Hence --hostname 9276383fe31e above. Omit it and the settings store cannot decrypt its own keys (section 9).
  2. The HF_TOKEN value.   3. The job directories. docker commit does capture /root/.omnivoice since it is in the writable layer — which also means your "slim" export carries 5.8 GB of old renders. Delete the job dirs first if you do not want them, but keep faprim01: it is your verification control.
  4. The exact Docker and driver versions. 29.4.1 and 580.126.09 today. A newer base AMI will differ. Usually fine, occasionally not.
  5. The swapfile and fstab entry. Recreate if you want it, though 24 GB of unused swap is not worth carrying.

11. Rehearsal: prove it works before you need it

The whole point of doing this early is that you get to find out what is wrong while the original still works. With the quota raised to 8 vCPUs you can run both machines at once, so a rehearsal costs one afternoon and about $0.40 per hour of instance time.

  1. Do steps 5.1 to 5.10 fully, ending with a running instance in the new account.
  2. Run the tier-1 fingerprint check (7.1). This alone proves the disk arrived intact.
  3. Run the tier-2 settings check (7.2), and the proxy and Google checks from 5.12.
  4. Dub one short video end to end on the new box and listen to it. Not the reference job — something small, so it is quick.
  5. Stop the new instance. Do not terminate it: stopping preserves the volume and costs only EBS (~$12/month for 150 GiB gp3), so on the day you actually cut over there is nothing left to do but start it.
  6. Keep using the old box as normal until then.

If the rehearsal succeeds, the real cutover is: stop the old box, start the new one, re-run aws_lock_ip.ps1, done. If it fails, you have found out at zero risk, with the working machine still sitting there.

13. If it goes wrong: rollback and troubleshooting

13.1 Rollback is trivial, by design

Nothing in section 5 modifies the old instance except stopping and starting it, which has been done repeatedly with all fingerprints verified identical afterwards. If anything about the new box is wrong: leave it alone, start the old box, and carry on. The old machine is not degraded by the migration in any way.

The one genuinely dangerous command in this whole area is terminate-instances. The root volume has DeleteOnTermination = true, so terminating destroys 150 GiB containing the patched backend, the models and every job. Do not terminate the old instance until the new one has passed section 7 and the new account owns its own AMI copy (step 5.7). Even then, prefer stopping it for a while first.

13.3 Operating rules that still apply on the new box

  • Never restart the app mid-render. Module defaults are read at import time, so a change needs a reload — but only when idle.
  • Write a .sh and ship it with rsh.ps1. Never build bash inside PowerShell strings; it has produced both a false invariant failure and a wrong measurement (an ASR count of 714 against a true 76).
  • docker exec without -i discards a heredoc silently. Use docker cp, or -i with bash -s as rsh.ps1 does.
  • The console is cp1252. No non-ASCII in .sh files; print codepoints rather than Devanagari or Telugu.
  • Verify the invariants before and after every change, not just after.

14. Slimming down on the way across (optional)

The migration is the natural moment to shed dead weight, because a smaller volume means a faster copy and a permanently smaller EBS bill. It is also the moment when a mistake is most expensive, so this section is deliberately conservative: do the cleanup on the old box, verify the pipeline still passes section 7, and only then take the AMI. Never clean up on the new box before you have proved it works.

Doing only the four "safe" rows takes the used figure from 115 GB to roughly 77 GB, which comfortably fits a 100 GiB root volume and saves about $4/month forever. Add the "verify first" rows and you are near 60 GB, but only attempt those if you are willing to run a full verification render afterwards.

Sequence matters. A new root volume may be larger than the snapshot but never smaller. So the order is: clean up on the old box → verify with section 7 → take the AMI → launch with the smaller VolumeSize. If you take the AMI first, you are stuck with 150 GiB.
