Dubbing Website — Backend Plan

Users upload a video, choose a language, and get a dubbed video back — built around the existing pipeline without changing it
The one rule this whole design is built around. The dubbing pipeline is finished and correct. This plan does not modify a single line of it. The website talks to VoiceStudio through the same HTTP endpoints your browser already drives, in the same order, with the same settings. 1. What we are building, and what stays untouched

1.1 The product, in one paragraph

A visitor signs up, logs in, uploads a video, picks the language they want it dubbed into, and pays or spends quota. The job goes into a queue. The GPU machine starts by itself, the existing pipeline transcribes, translates and renders exactly as it does today, and the finished video appears in the user's dashboard for download. When nobody has work for the GPU for five minutes, it shuts itself down so it costs nothing.

1.2 The boundary that protects the pipeline

There are two systems, and the line between them is a network call:

Existing — do not touchNew — everything we build
The GPU box: VoiceStudio 0.4.2, the patched backend, chirp_3, forced alignment, the onset snap, the speaker cloning, all the settings in the pipeline handbookWeb API, database, login, payments, upload handling, the job queue, the GPU on/off controller, the website itself
Reached only through its own HTTP API on port 3900Calls that API the same way the browser does
Zero code changesAll new code, in its own private repository
Why quality cannot drop. The pipeline's behaviour is decided by the module defaults inside the container — recogniser, timing source, star tokens, band gate, snap settings. We change none of them and we set no environment variables. We send the same requests with the same parameters. Our job is scheduling and plumbing, not dubbing.

1.3 The one honest complication

Today the translated text lives in your browser. The job row in VoiceStudio's own database has tracks: [] and no translated fields — which is why refreshing the page loses the translation. A server cannot rely on a browser to hold that. So our backend must keep the transcript and translation itself, between the translate call and the render call. That is new orchestration on our side, not a change to the pipeline: we store what the pipeline returns and hand it back verbatim when we ask it to render. Whatever bytes come out of translate are the bytes that go into render.

4. The complete journey of one video

Every step names who does the work. Notice that the browser never speaks to the GPU box, and never receives anything except its own data and short-lived URLs.

4.1 Signing up and logging in

  1. Browser posts email and password to POST /api/auth/signup over HTTPS.
  2. API checks the password against a minimum strength rule and against a list of known-breached passwords, hashes it with Argon2id, creates the user as unverified, and emails a single-use verification link that expires in 24 hours.
  3. API returns success without saying whether the email already existed — otherwise the endpoint becomes a tool for discovering who has an account.
  4. On POST /api/auth/login, the API verifies the hash, then creates a session: a 256-bit random token. Only a SHA-256 hash of that token is stored. The token itself goes back as an HttpOnly; Secure; SameSite=Lax cookie.
  5. Every later request carries the cookie automatically. JavaScript cannot read it, so a cross-site scripting bug cannot steal the session.

4.2 Uploading a video

  1. Browser asks POST /api/uploads for permission, sending the filename, size and content type.
  2. API checks the session, checks the user's plan and remaining quota, checks the size against the plan's ceiling, then generates a presigned S3 PUT URL: valid 15 minutes, one specific object key uploads/{user_id}/{upload_id}.mp4, with the content length and type pinned.
  3. Browser uploads directly to S3. The video never passes through our API server.
  4. Browser calls POST /api/jobs with the upload id, source language, target language.
  5. API verifies the object actually exists and belongs to that user, runs ffprobe against it to read the real duration and codec — never trusting the file extension — rejects anything that is not really a video or exceeds the plan's duration limit, then writes a jobs row with state queued and returns the job id.

4.3 The job runs

  1. API, on enqueue, checks whether the GPU is running. If not, it calls StartInstances and marks the job preparing.
  2. Worker claims exactly one queued job with SELECT ... FOR UPDATE SKIP LOCKED, so two workers can never take the same job even if we run two by accident.
  3. Worker waits for the GPU box to answer /sysinfo on the private network, with a timeout and a bounded number of retries.
  4. Worker copies the video from S3 to the GPU box and drives VoiceStudio exactly as the browser does: upload, transcribe, translate, generate, export. It reads progress from the task stream and writes it to job_events so the user sees real progress.
  5. Crucially, the worker stores the transcript and the translated lines in our database between the translate and generate calls, then passes them back verbatim. This is the piece the browser used to do.
  6. When the mux completes, the worker pulls the finished file to S3 under outputs/{user_id}/{job_id}.mp4, records the duration billed in usage_ledger, sets the job done, and sends the "ready" email.
  7. Worker deletes the working copies from the GPU box, so user videos do not accumulate on a shared machine.

4.4 Getting the result

  1. Browser polls GET /api/jobs/{id} (or holds an SSE stream) and shows progress.
  2. When done, it asks GET /api/jobs/{id}/download. The API checks the session, checks that this job belongs to this user, and returns a presigned GET URL valid for 15 minutes.
  3. The bucket itself stays private forever. There is no public link, and an old URL stops working.

5. GPU on demand: start on upload, stop after 5 idle minutes

This is the part that decides the bill, and the part where a bug is most expensive — either money burned on an idle GPU, or a render killed halfway.

5.1 The rule, stated precisely

START  when a job is created and no GPU instance is running.

STOP   when ALL of these are true:
         - no job is in state 'preparing' or 'processing'
         - no job is in state 'queued'
         - the last job finished at least 5 minutes ago
         - the instance is actually running

The check runs every minute. Because it requires the queue to be empty as well as idle, a burst of uploads keeps the machine up and processes them back to back, which is both faster for users and cheaper than starting and stopping repeatedly.

5.2 How it is implemented

PieceWhat it does
StartInside POST /api/jobs. Reads the gpu_state row, and if the instance is not running calls EC2 StartInstances. Idempotent: two simultaneous uploads cannot start two machines, because the row is locked while the decision is made.
ReadinessThe worker polls http://<private-ip>:3900/sysinfo. The container's restart policy is already unless-stopped, so it comes back on boot by itself. Expect about 2 minutes for the instance plus about 1 minute for the model to load.
StopAn EventBridge rule every 1 minute invokes a small Lambda. The Lambda reads the database, applies the four conditions above, and calls StopInstances. It lives outside the API on purpose, so an API restart or crash cannot leave the GPU running.
TruthThe database is the only source of truth for "is there work". The Lambda never guesses from CPU load, which would be fooled by a model still loading.

5.3 The safety rules that stop this being dangerous

  • Never stop with work in flight. The Lambda refuses if any job is preparing or processing. A render takes about 7 minutes for 156 lines; killing it wastes the whole job.
  • If the database is unreachable, do nothing. Failing to stop costs money; stopping wrongly destroys a user's job. So the failure mode is deliberately the expensive-but-safe one, and it raises an alarm.
  • A stuck job must not hold the GPU for ever. Any job processing for longer than a generous ceiling (say 90 minutes) is marked failed, the user is told, and an alert fires. Without this, one bad job pins a GPU indefinitely.
  • A cost alarm independent of all of it. A CloudWatch alarm on the instance running more than N hours in a day emails you regardless of what the software believes.
  • Graceful shutdown. Stopping the instance sends SIGTERM to the container. We never run docker stop ourselves — with the unless-stopped policy a manually stopped container would not restart on the next boot, which would look like a total outage.

5.4 What the user sees while the GPU boots

Honest progress, not a spinner that lies: "Starting the dubbing engine (about 2 minutes)", then transcription, translation and rendering percentages from the real task stream. For a 12-minute video the whole thing is roughly 20 minutes, so the flow is "we will email you", with the page updating live if they stay.

TablePurpose
audit_logWho did what, when, from where: logins, password changes, plan changes, admin actions, job deletions. Append-only, never updated.
Two design decisions worth defending. First, the queue is a table rather than a separate queue service — with one GPU, correctness means strict serialisation, and FOR UPDATE SKIP LOCKED gives exactly that with nothing extra to migrate. Second, quota is a ledger rather than a counter. A counter that gets decremented is impossible to reconcile when something half-fails; a ledger can always be recomputed and explained to a customer who disputes a charge.

7. Security, in detail

7.1 Passwords

  • Argon2id, memory 64 MB, 3 iterations, 4 lanes. This is the current recommendation and is deliberately slow and memory-hungry so that a stolen database cannot be brute-forced cheaply on GPUs.
  • Each hash carries its own random salt, handled by the library.
  • Minimum 10 characters, checked against a known-breached password list. No forced special characters — that produces predictable passwords.
  • Passwords are never logged, never returned by any endpoint, and never sent by email.
  • On password change or reset, every session for that user is revoked, so a stolen cookie dies with the password.

7.2 Sessions and cookies

PropertyValueWhat it prevents
Token256-bit random, from the OS random sourceGuessing
StorageOnly SHA-256 of the token, in sessionsA database leak does not yield usable session tokens
HttpOnlyonJavaScript cannot read the cookie, so an XSS bug cannot steal the session
SecureonNever sent over plain HTTP
SameSiteLaxThe cookie is not attached to cross-site POSTs, killing most CSRF
Path / Domain/, host-only (no Domain attribute)Subdomains cannot read it
Lifetime7 days sliding, 30 days absoluteAn abandoned session eventually dies no matter what
RotationNew token issued on login and on privilege changeSession fixation

Why sessions and not JWTs. A JWT cannot be revoked before it expires without keeping a server-side blocklist — at which point you have a session table with extra steps. Opaque tokens in a table mean "log this device out now" actually works.

7.3 CSRF, CORS and headers

  • SameSite=Lax plus a required X-CSRF-Token header on every state-changing request, matching a per-session value. Two independent defences, because browsers and SameSite behaviour vary.
  • CORS allows exactly one origin — our own site — with credentials. No wildcard, ever.
  • Response headers: Strict-Transport-Security with a long max-age, Content-Security-Policy with no inline scripts, X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, and X-Frame-Options: DENY.

7.4 Authorization — the rule that prevents users seeing each other's videos

Every query that touches user data is scoped by the session's user id, in the query itself. 
SELECT * FROM jobs WHERE id = :job_id AND user_id = :session_user_id
Not "fetch the job, then compare" — that pattern is how one forgotten if becomes a data breach. Job ids are UUIDs so they cannot be enumerated, but that is a second layer, never the defence itself. A job that does not belong to the caller returns 404, not 403, so the API does not confirm that someone else's job exists. Admin endpoints, if we add them, live under a separate path with a separate role check and are written to audit_log every time.

7.5 Secrets — how the VoiceStudio keys never leak

This was an explicit requirement, so here is the full chain.

SecretLives inReachesNever
Database passwordSecrets Manager, rotatedAPI and worker at boot, by IAM roleNot in code, git, or any client
Razorpay / Stripe keysSecrets ManagerAPI onlyThe browser only ever gets a checkout session id, never a secret key
SES credentialsIAM role, no key at allAPI—
GPU box: HF token, Google service account, Gemini proxy keySecrets ManagerDelivered to the instance at boot by its own IAM instance profileNever baked into an AMI, never in a Docker image, never in git, never sent to the browser
Session signing / CSRF secretSecrets ManagerAPI only—
  • The frontend receives exactly three kinds of thing: its own session cookie, its own data, and presigned URLs that work for one object for 15 minutes. Nothing else. There is no configuration file shipped to the browser containing any key.
  • The GPU box's HF token is currently visible in the container environment. It should be rotated before launch and delivered from Secrets Manager thereafter, because anything in a container environment shows up in logs and diagnostics sooner or later.
  • Presigned URLs are treated as secrets. They contain a signature, so they are never written to logs and never put in a URL that could end up in a referrer header.
  • Git is scanned. A gitleaks pre-commit hook plus a CI scan on every push. Secret scanning and push protection enabled on the GitHub repository.

7.6 Protecting the GPU box

VoiceStudio has no authentication of any kind. A GET to port 3900 returns 200 to anyone who can reach it, and the box holds an AWS instance role. That is acceptable today only because your firewall allows exactly one home IP address. A public website changes the picture completely, so:
  • The GPU instance gets no public IP and sits in a private subnet.
  • Its security group allows port 3900 only from the worker's security group — not from an IP range, and not from the internet.
  • Its IAM role is narrowed to only what the pipeline genuinely needs.
  • Outbound access for Google Speech and the Gemini proxy goes through a NAT gateway, or the instance keeps a public IP with no inbound rules at all if we want to avoid the NAT cost. Both are safe for inbound; the difference is cost and egress control.
  • The website's API never proxies arbitrary requests to it.

7.7 Data at rest and in transit

  • S3: Block Public Access on at the account level, SSE-KMS with a customer-managed key, a bucket policy that denies any request not using TLS, versioning on, and access logging.
  • RDS: private subnet, not publicly accessible, encrypted at rest with KMS, rds.force_ssl so unencrypted connections are refused, automated backups with point-in-time recovery, deletion protection on.
  • In transit: TLS 1.2 or better everywhere, including inside the VPC to RDS.
  • Lifecycle: uploaded source videos deleted after 7 days, outputs after 30 days (or per plan). Less stored data is less to leak, and it keeps the bill down.
  • Deletion: an account deletion request removes S3 objects, job rows and personal fields, and leaves only anonymised billing records that the law requires.

7.8 Upload safety

  • Size and duration capped per plan, enforced server-side after upload using ffprobe, because a client can claim anything.
  • Content type pinned in the presigned URL; the real container and codec verified afterwards.
  • The stored object key is generated by us from the user id and a UUID. The user's filename is never used as a path — that is how path traversal happens. The original name is kept as a display label only.
  • A pathological input — a 4-hour video on a free plan, a file that probes as audio-only, a video with no speech — is rejected with a clear message before any GPU time is spent.

7.10 Logging — and what must never be logged

  • Structured JSON logs to CloudWatch, with a request id threaded through, retention set explicitly.
  • Never logged: passwords, session tokens or cookies, reset tokens, presigned URLs, payment card data, full request bodies on auth endpoints.
  • Always logged: user id (not email) for actions, job state changes, admin actions, webhook signature results, and every authorization failure.
  • Errors go to Sentry with PII scrubbing on.

8. Subscriptions, plans and quota

8.1 How money is handled without touching card data

  1. The user picks a plan. Our API creates a checkout session with Razorpay or Stripe and returns only an opaque id.
  2. The provider's own hosted page takes the card details. They never reach our servers, which keeps us out of PCI scope entirely.
  3. The provider calls POST /api/billing/webhook. We verify the signature before reading the body, record the event id in webhook_events, and ignore duplicates.
  4. Only then does the subscription become active. The browser is never believed about payment. A user who closes the tab mid-payment is still upgraded when the webhook lands; a user who forges a "success" call to our API achieves nothing.

8.2 Quota, enforced in one place

minutes_used_this_period = SUM(usage_ledger.minutes_charged) since period start
minutes_left             = plan.minutes_per_period - minutes_used_this_period

Checked at two moments: when the upload URL is requested (fail early, before a big upload) and again when the job is created (because time passes and other jobs may have run). Billing is on video duration as measured by ffprobe, decided before work starts, so a user always knows the cost in advance. A failed job writes no usage row — nobody pays for our bugs.

10. Moving everything to another AWS account

This was a hard requirement, so it shapes several earlier decisions rather than being an afterthought. The design rule: nothing that matters may exist only as a setting somebody clicked.

10.1 What makes it possible

DecisionWhy it helps migration
Everything in TerraformA new account is terraform apply with a different account id, region and domain. No manual rebuild.
No hardcoded account ids or ARNsThey come from variables and data sources, so nothing has to be found and edited.
Our own authentication instead of CognitoPassword hashes move with the database. Cognito cannot export them, which would force every user to reset their password — a migration that loses customers is not a migration.
Plain PostgreSQLpg_dump and pg_restore work between any two accounts, and between AWS and anything else.
Alembic migrations in gitThe schema can be rebuilt from scratch and verified independently of any dump.
Queue inside PostgresNothing extra to drain, recreate or reconcile.
Images rebuilt from sourceThe new account's registry is filled from git, not copied from the old account.
Secrets listed by name in Terraform, values entered separatelyThe new account gets its own secret values; nothing sensitive travels in a repository.

10.2 The migration runbook

  1. In the new account, create the Terraform state bucket and lock table, then terraform apply with the new variables. Infrastructure exists, empty.
  2. Create the secrets in the new account's Secrets Manager (new database password, new provider keys, rotated GPU tokens).
  3. Build and push the images from git to the new account's ECR.
  4. Run Alembic against the new database to create the schema.
  5. Freeze writes: put the API in maintenance mode and let running jobs finish.
  6. pg_dump the old database, pg_restore into the new one, then verify row counts table by table and spot-check a few users and jobs.
  7. aws s3 sync both buckets across accounts (a temporary cross-account bucket policy, removed afterwards). Verify object counts and a few checksums. Note KMS: objects are re-encrypted with the new account's key on copy — expected, and worth allowing time for on large buckets.
  8. Create the GPU instance in the new account from the same AMI or a fresh build, and confirm the pipeline handbook's fingerprints match. This is the step to be most careful with: the patched backend must arrive byte-identical, verified by the MD5s in the handbook.
  9. Point DNS at the new front door. Watch error rates.
  10. Keep the old account read-only for a fortnight before deleting anything.
Rehearse it once, into a throwaway account, before you need it. A migration plan that has never been executed is a hypothesis. The rehearsal also produces the real timings, which is what tells you how long the maintenance window has to be.

15. Questions I need answered before writing code

  1. Who are the users? India only (Razorpay, UPI, INR) or international (Stripe, USD)? This decides the payment integration.
  2. Which language pairs do we advertise? The pipeline handles seven, but English placement is measurably weaker and there is an unshipped English-only fix. We should not sell what we have not validated.
  3. Longest video allowed? This sets timeouts, storage and the free-tier limit. Your test material was 3–13 minutes.
  4. Can the user edit the transcript or translation before rendering? A big product decision: it is where dubbing quality is really won, but it roughly doubles the backend work because the job becomes multi-step with human review in the middle.
  5. Free tier? If yes, expect abuse and budget for a CAPTCHA and tighter limits.
  6. Retention? How long do we keep a user's source video and output.
  7. Domain name, and do you already have one in Route 53?
  8. How much waiting is acceptable before we buy a second GPU? That number is the trigger for a scaling decision, and it is better agreed now than during an outage.

16. What I have not verified

  • The exact VoiceStudio API contract. I know the endpoints your browser calls — /dub/transcribe, /dub/translate, /dub/generate/{job}, /tasks/stream/{task}, /dub/media/{job}, /tasks/cancel/{task} — but not every required field of every request body. Before any code is written, one short discovery pass with the box running should capture the precise request and response shapes, ideally by recording a real session. Guessing here would produce a worker that half-works.
  • Whether uploading via the API path behaves identically to the desktop client's path. It should, but it must be proved with one end-to-end job whose output is compared against a known-good render.
  • Boot-to-ready time was inferred from logs at roughly 2 minutes plus about a minute of model load. Worth measuring properly, because it is what the user waits through.
  • Concurrency inside VoiceStudio. I have assumed strictly one job at a time. That matches one GPU and everything observed, but it has not been tested by deliberately sending two.
  • Cost figures are estimates from published pricing, not from your bill.
  • The IAM policy update failed the last time the firewall script ran (policy update FAILED). Harmless for the work done since, because none of it used AWS APIs from the box — but it must be fixed before anything relies on Amazon Translate or Bedrock.
The shortest summary. Build a normal, boring, well-secured web application in front of the dubbing engine, and let it treat the engine as a black box it starts, feeds, reads and stops. Every hard requirement you gave — easy account migration, no leaked keys, secure user data, database access for you, automatic GPU shutdown — is satisfied by a specific decision above rather than by good intentions: Terraform, our own auth in Postgres, secrets only in Secrets Manager, an SSM tunnel, and a watchdog that refuses to stop a machine that is working.
