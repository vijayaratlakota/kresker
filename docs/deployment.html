1   The shape of the system, in one picture

Four tiers. The unusual one is the third: the GPU is a machine that is switched off most of the time and is started by an upload, which is the single biggest cost decision in the design.

BROWSER YOUR MACHINE / SERVER AWS ap-south-1 ------------------------ --------------------------------------- ------------------ React SPA HTTPS +---------------------------------+ (Vite build, -------> | uvicorn : FastAPI | dist/ static) | + dub-worker (thread) | | + gpu-watchdog (thread) | vs_session cookie | | +----------------+ + X-CSRF-Token | SQLite data/live.db (WAL) | | g4dn.xlarge | | Files data/uploads | | i-041b48c5... | | data/outputs | | | | data/mail | | Docker | +---------------------------------+ | 9276383fe31e | | | | :3900 | ssh -L 3900 | | aws ec2 | | (tunnel) +------------+ start/stop-instances| gemini-proxy | | +----------------+ v | 127.0.0.1:3900 ==== the tunnel IS the link ====--+ | Razorpay Resend Google OAuth v (payments) (email) (sign-in) Amazon Translate Amazon Bedrock Cloudflare R2 (video delivery, OFF by default)
The one thing to understand about the GPU link. The backend never talks to the box's public address. It opens an SSH tunnel and then talks to http://127.0.0.1:3900, which is the local end of that tunnel. This is deliberate: the box's public IP changes on every start, and the engine on port 3900 accepts no credentials at all — a plain GET returns 200 to anyone who can reach it. The tunnel plus a security-group rule locked to one address is the only thing protecting it.

2   What a single dub actually does, request by request

#StepWhat happens
1POST /api/uploads Session and CSRF checked, then the email-confirmed gate, then the rate limit. The GPU is started here, before a single byte is read (gpu.ensure_running(block=False)) so the ~6-minute warm-up runs underneath the upload instead of after it. The file is streamed to data/uploads/ and ffprobe measures the real duration — never the client's claim. Quota is checked against that measurement.
2POST /api/jobs One request, up to 8 languages. Charges the minute ledger for the total and creates every job row in one transaction, so a partial failure cannot charge for three and queue two.
3the worker claims it The dub-worker thread takes the oldest queued job under a lock plus a transaction, using a guarded UPDATE ... WHERE state='queued' and checking rowcount.
4engine: upload → transcribe POST /dub/upload, then the streaming transcribe endpoint. Per-read timeout of 900 s, not a total: the clone-building tail goes quiet for minutes and a total timeout cannot tell "working" from "wedged".
5engine: translate → generate Translation and the per-line voice generation. Refuses to render if no segment carries a profile_id (every line would use the stock voice) or if translation covered fewer lines than there are segments.
6download and verify Refuses to download unless engine.has_track() is true — /dub/download otherwise returns the original audio, and that has shipped as a finished dub before.
7store and stamp Written to data/outputs/<job>.mp4, optionally uploaded to R2, ISO-639-2 audio track tag applied, output_expires_at set from the plan's retention, "your dub is ready" emailed once (notified_done_at makes a retry free).
8GET /api/jobs/{id}/download Mints a short-lived signed token, 307-redirects to /dl/{token}, which either streams from local disk or redirects again to a presigned R2 URL.
9the box turns itself off 10 minutes after the last job finishes, if nothing is queued and no upload is in flight. See section 4.

3   The processes — what runs, where, and how it starts

The worker is not a separate service. One uvicorn process contains the API, the dub worker and the GPU watchdog as daemon threads. This is fine for one machine and is the single hardest limit on scaling: a second process on the same database would requeue jobs the first one is actively running. See section 11.

3.1   The API process

app/main.py's startup handler runs, in order: db.init_db(), billing.ensure_tables(), notify.ensure_tables(), site.ensure_tables(), worker.start(), gpu.start_watchdog(). So the process holds:

  • the FastAPI app;
  • a daemon thread dub-worker — claims jobs, drives the engine, and every ~300 idle seconds also runs the retention sweep and the billing sweep;
  • a daemon thread gpu-watchdog — first pass after 45 s, then every 60 s;
  • transient gpu-warmup threads, and the ssh child process holding the tunnel.

3.2   The three ways it gets started

ScriptPurposeCommand and notes
backend/run.ps1Local, fake engine uvicorn app.main:app --host 127.0.0.1 --port 8080. Sets VS_ENGINE_MODE=fake and VS_COOKIE_INSECURE=1. Uses data/app.db. Note: the script's default port is 8080 while the README says 8099.
backend/go_live.ps1The real pipeline Starts the instance, waits for SSH, checks /sysinfo, starts the container if needed, reports gemini-proxy, opens the tunnel in its own minimised window, probes the mail key, then uvicorn app.main:app --host 127.0.0.1 --port 8099 against data/live.db.
backend/stop_live.ps1Stop paying Kills every ssh process, then aws ec2 stop-instances.
Both start scripts bind to --host 127.0.0.1. As configured, nothing is reachable from off the machine. That is correct for development and is one of the things that has to change for production — along with the reverse proxy that would then be in front of it.

3.3   The watchdog, which is deliberately outside the API

install_watchdog.ps1 registers a Windows scheduled task, "VoiceStudio GPU watchdog", every 5 minutes, running pythonw.exe backend/watchdog.py. It exists because the in-process watchdog dies with the API — and an API crash that leaves a ₹47/hour machine running is exactly the failure worth a second mechanism.

Two details in that script were learned the hard way and are worth not re-discovering: it registers via XML because schtasks /tr silently splits the command on the first space (the path contains one, so every run failed while the task reported Ready), and it uses pythonw.exe because a console program under InteractiveToken pops a visible window every five minutes.

watchdog.py refuses to run if the database file does not exist — an empty database is indistinguishable from an idle one, and it would stop a box that was busy.

3.4   The frontend

React 18 + Vite 6 + Tailwind 4. npm run build emits frontend/dist/. In development the Vite dev server runs on 5173 and proxies /api, /dl, /robots.txt, /sitemap.xml, /db, /docs and /openapi.json to the backend — same-origin on purpose, so the session cookie works with no CORS and no SameSite exemption.

Nothing in this repository serves frontend/dist. The backend mounts only its own app/static operator pages. In production the built files need a web server or a CDN in front, and that configuration does not exist yet. See section 11.

4.1   Starting

gpu.ensure_running(). Triggered by an upload, non-blocking so the customer never waits on a boot. It tests whether the engine answers, not whether we own the tunnel — a tunnel opened by hand in another window is deliberately tolerated. Then: start-instances → poll for running (up to 600 s) → wait for SSH (180 s) → open the tunnel → poll /sysinfo (up to 420 s), and if it does not answer, docker start the existing container once.

A running instance is not a running application. The container does not reliably come back on boot, so the readiness gate is "/sysinfo answers", not "the instance is running". Nothing is ever rebuilt or edited — only started.

4.2   Stopping

gpu.maybe_stop() runs from both watchdogs and refuses while hold_reason() returns anything. All four conditions are answered from the database only, deliberately, so the same logic can move into a Lambda unchanged:

  1. no job in claimed / preparing / transcribing / translating / rendering / exporting;
  2. no job queued;
  3. no upload accepted in the last 20 minutes that has not become a job;
  4. the last work finished at least 10 minutes ago.

Ten minutes rather than five because a boot costs about six minutes of GPU time either way — so shutting down just before the next job arrives is the most expensive thing the watchdog can do.

4.3   The network rule that actually matters

The engine on :3900 takes no credentials. Once the box holds its instance role, whoever can reach that port can drive Amazon Translate and Bedrock on our bill. aws_lock_ip.ps1 restricts 3900, 3000 and 22 to the operator machine's current /32 and patches the aws:SourceIp condition on the IAM policy. It must be re-run after every stop/start, because the public IP changes. The group previously allowed two ISP pool ranges — about 9,200 addresses.

The box's IAM role OmniVoiceTranslateRole grants translate:TranslateText plus Bedrock invoke on five pinned models (Mistral Large 3, DeepSeek v3.2, Kimi K2.5, Gemma-3-12b-it, Qwen3-235B), both statements conditioned on the box's source IP.

5   The database

Engine SQLite, stdlib sqlite3, no ORM
File backend/data/live.db in production use; app.db for fake-mode development
Journal WAL, foreign_keys=ON, busy_timeout=30000
Connections one per thread (threading.local())
Writes serialised through a process-wide RLock; reads are not locked
Postgres FUTURE postgres_schema.sql exists and is held column-for-column against the SQLite schema by a test, but nothing connects to Postgres

SQLite allows exactly one writer, which is why the write lock exists: a background worker plus web requests would otherwise collide as database is locked under load.

5.1   Migrations

db.init_db() runs on every startup: apply schema.sql (idempotent, CREATE TABLE IF NOT EXISTS) → apply an additive list of ALTER TABLE ADD COLUMN steps, skipping any column already present → create migrated-column indexes → seed the plans and the singleton gpu_state row.

There is no version table and no down-migration, deliberately: the interesting case is a database arriving from somewhere else, and that database has no idea which migrations it has seen. Idempotent-by-inspection handles it; a version counter does not.

One migration is worth naming because it protects existing customers: email_verified_at is backfilled to each user's creation time, because adding a NULL column would otherwise have locked every existing account out of uploading on the next restart.

5.3   Backup and moving installations

app/portability.py exports the database as JSONL per table, plus copies of both schema files and a manifest. The manifest holds a fingerprint of the live column layout (not of the schema file, so drift is detectable), per-table row counts, order-independent digests, and sums — total minutes charged and total cash — because a partial restore can produce the right row count with the wrong contents.

  • No secret ever enters the archive. Keys are reported by name and by whether they are set.
  • Sessions are skipped — carrying them means carrying live credentials in a file that gets copied around. Everyone signs in again.
  • restore() refuses to touch an existing file.
  • The archive is the database only. Finished videos on local disk have to be copied separately; with R2 on they do not move at all.
Gap: four tables are missing from the export list — consent_records, inbox_messages, admin_access_log, app_settings. A move would lose the consent ledger and the rights-request inbox. Both are DPDP evidence.

Paths are stored relative to the data directory, in POSIX form. Rows used to hold C:\video translator\backend\data\outputs\<job>.mp4; restore that into a Linux container and nothing errors at restore time — downloads simply 410 later, one customer at a time.

6.1   Cloudflare R2 OFF BY DEFAULT

Enabled only when VS_R2_ENABLED=1 and all four credentials are present in %USERPROFILE%\.secrets\r2.env. Keys are dubs/<job_id>/dubbed_<lang>.mp4. Downloads are presigned URLs, 300 s by default. An upload failure never raises — the local copy stays deliverable.

Why it matters commercially: egress from R2 is free at any volume, which is what makes "unlimited downloads" cost nothing beyond storage. Until it is switched on, every download is served from the origin machine's bandwidth.

10   Security posture as deployed

ControlAs implemented
SessionServer-side table. The browser gets sid.raw; only sha256(raw) is stored. Cookie vs_session: httpOnly, Secure (unless opted out), SameSite=lax, 7 days. Compared with hmac.compare_digest
CSRFA per-session random value compared against the X-CSRF-Token header on every mutation. Two independent defences, because SameSite behaviour varies by browser
Passwordsscrypt, n=2^14, r=8, 128 MiB maxmem passed explicitly (OpenSSL's default of 32 MB refused the cost outright). Parameters stored in the hash, so the cost can be raised later without invalidating anyone
Response headersCSP (script-src 'self', frame-ancestors 'none', object-src 'none', base-uri 'none'), X-Frame-Options DENY, nosniff, Referrer-Policy, Permissions-Policy, COOP. HSTS only when production and https
Rate limits16 buckets, in-process sliding window, 429 with Retry-After. Login is limited per IP and per account: per IP alone lets one attacker work through many accounts, per account alone lets a botnet work through one
Client IPX-Forwarded-For honoured only from a peer in the trusted list. Otherwise the header hands the caller control of their own rate-limit key and makes audited IPs forgeable
AuthorizationOwnership is scoped inside the query, not checked after. Admin routes answer 404. Money-moving admin actions demand the password again
ErrorsFull traceback logged, a 12-hex reference disclosed. A non-string, non-flat-dict exception detail becomes "request failed" so an internal object cannot serialise itself into a response
Uploads4 GiB cap enforced while streaming; type and duration from ffprobe, never from the client; an unreadable file is deleted rather than left on disk
Verified, not asserted. 807 backend checks across 18 suites and 458 frontend checks, all passing. Response headers have their own suite because nothing else can catch them — an HTTP client does not enforce a CSP, so a policy that would leave the admin browser rendering with every button dead passes every other test.

11.2   Scaling limits, stated plainly

  • Exactly one worker. Startup treats every active job as abandoned and requeues it — correct for one process, and wrong the moment there are two: worker B starting would requeue what worker A is running. That deployment needs a lease first.
  • One writer. SQLite plus a process-wide write lock. Fine for one machine; the Postgres schema exists for when it is not.
  • In-process state that will not survive scaling out: the rate-limit windows, the SSH tunnel handle, the AWS describe cache.

11.3   Compliance

The admin panel's DPDP checklist reports six items and currently fails several: the grievance contact is unpublished, the notice version is a draft, the public base URL is not https, and signup consent is not enforced server-side. Two items marked LEGAL REVIEW need a lawyer rather than a developer: the 30-day rights-response default, and the retention basis and period for payment records.

One real bug in the checklist itself. It tests VS_COOKIE_SECURE=1, but the application reads VS_COOKIE_INSECURE. So the check can never pass, and setting VS_COOKIE_SECURE=1 alongside VS_COOKIE_INSECURE=1 would report "Secure" while the cookie is not. Worth fixing before the checklist is trusted as evidence.

11.4   Licensing

The interface font, Century Gothic Pro, is a commercial Adobe/Monotype face and the copy in public/fonts/ is not licensed for web distribution. Before this is public: buy a webfont licence, or swap the @font-face source for an open geometric alternative (Questrial, Jost, Outfit). Nothing outside that one block names a font, so the swap is a single edit.

12   Deploying, and rolling back

12.1   Today's procedure

# 1. Verify before anything moves. Both must be zero failures.
cd backend;  .\_verify_all.ps1                 # 18 suites, 807 checks
cd frontend; npx tsc -b --force && npm run build
             python _verify_ui.py http://localhost:5176   # 458 checks

# 2. Confirm the tuned pipeline is untouched. This fingerprint must not change.
python -c "from app import preset; print(preset.preset_only_fingerprint())"
#   853a9e63a12b31be7026f27e52dff6b929e1eb9c8e1bf15fe793a16453356992
git diff --name-only -- pipeline _box_src backup backend/app/preset.py   # must be empty

# 3. Archive the database before touching it.
POST /api/admin/export        # then copy data/uploads and data/outputs separately

# 4. Bring the pipeline up.
cd backend; .\go_live.ps1

# 5. Re-lock the box's security group. The public IP changed when it started.
.\aws_lock_ip.ps1 -Apply

# 6. When finished, stop paying.
.\stop_live.ps1

12.2   Rolling back

  • Code: git. The preset fingerprint is the check that the pipeline came back identical.
  • Schema: there are no down-migrations. Every step is additive, so an older binary tolerates a newer database — an extra column is ignored. The reverse is not true, so roll code back before data.
  • Data: restore an archive into a new file; restore refuses to overwrite. Then compare the manifest's totals, not just its row counts.
  • Emergency: maintenance mode, from the admin panel. The public gets a 503 with Retry-After; admins still see the real site; robots.txt and the sitemap keep serving, because a 503 there makes Google drop the site.
