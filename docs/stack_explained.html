2. The pieces, one at a time

Python and FastAPI — the counter staff

The program that answers every request from the website.

What an API is. When you click "Upload" on a website, the page does not do the work itself. It sends a message to a program on a server: "this user wants to upload a video." That program is the API. It decides whether you are allowed, does the work, and sends an answer back. Every app on your phone works this way.

What FastAPI is. A toolkit for writing that program in the Python language. It handles the boring, error-prone parts — reading the incoming message, checking the fields are the right type, sending a clean reply.

Why we chose it. Three reasons, in order of importance:

  • Your dubbing pipeline is already written in Python. One language across the whole project means one set of skills to hire for and one set of habits.
  • It checks incoming data automatically. If someone sends video_length: "banana", FastAPI rejects it before our code sees it. That is a security feature, not a convenience — a large share of real break-ins start with unexpected input.
  • It is ordinary and widely used, so problems have known answers.

What it does here: signup, login, issuing upload links, creating jobs, reporting progress, handling payments.

What it never does: dubbing. It hands work to the queue and answers immediately, because a web request cannot sit there for 20 minutes.

PostgreSQL on Amazon RDS — the register

The organised memory of the business.

What a database is. A set of tables, each like a spreadsheet with fixed columns. One table for people, one for orders, one for payments. Unlike a spreadsheet it can be read and written by many programs at once without going wrong.

What "on RDS" means. RDS is Amazon running the database for you: backups, security patches, and restoring to any point in the last few days if something goes badly wrong. Without it, somebody has to remember to do all of that.

Why PostgreSQL and not MongoDB. One concrete reason: money has to add up. A customer's remaining minutes is a sum of what they bought minus what they used, and two things must never happen at once in a way that produces the wrong total. Postgres is built for exactly this and guarantees it. Since subscriptions, payments and quota are the parts where a bug costs you money or a refund argument, that guarantee is worth more than familiarity.

The second reason: moving house. You asked that everything be movable to another AWS account. Postgres can be copied out and copied in with two standard commands, taking every user and password with it.

What it stores: users, sessions, jobs, the queue, plans, subscriptions, payments, minutes used, audit trail.

What it never stores: the videos themselves. They are far too big; only the note saying where each one lives.

Reachable from the internet: no. Never. Only our own programs can talk to it.

Amazon S3 — the shelf at the back

Where the big files live.

What it is. Unlimited file storage. You put a file in with a name, you get it back later. It is not a hard disk attached to a server; it is a service, so it never fills up and never needs replacing.

Why not just keep videos on the API server. Three problems that all bite at once. A server has a fixed disk that fills. If the server is replaced — which happens routinely — the files vanish. And a 500 MB upload passing through the server ties up memory that other users need. S3 solves all three.

The clever part: the browser uploads straight to S3. Our API does not receive the video at all. Instead it hands the browser a presigned link: a web address with a signature attached that says "whoever holds this may write one file, to this exact name, for the next 15 minutes, and nothing else." After 15 minutes it is dead. The video goes browser → S3 directly, and our small API server is never the bottleneck.

Downloads work the same way in reverse. When a dub is ready, the API checks it is really your job and hands you a 15-minute read link. The bucket itself stays completely private — there is no public address for anybody's video, ever.

What it stores: uploaded source videos, finished dubbed videos.

Encrypted: yes, on disk, with a key that belongs to your account.

Automatic cleaning: sources deleted after 7 days, outputs after 30. Less stored is less to leak, and a smaller bill.

ECS Fargate — where our program actually runs

The place the counter staff stand.

First, what a container is. A container is your program packed together with everything it needs to run — the exact Python version, the exact libraries. Like a shipping container: whatever machine it lands on, the contents behave identically. This is what kills the classic complaint "it worked on my laptop". Your dubbing engine is already in a container called omnivoice, so you have seen this work.

What Fargate is. Amazon runs your container for you. You say "run this, give it this much memory", and there is no server that you own, log into, or patch. That matters more than it sounds: an unpatched server is one of the most common ways small companies get broken into, and here there is no server to forget about.

Why not a normal server. You could rent an ordinary virtual machine and run the program on it, and it would be cheaper — see section 7, where I lay that option out honestly. The trade is that you become responsible for security updates, and replacing a broken machine becomes a manual job at a bad moment.

What runs here: two things from the same container image — the API (answers people) and the worker (does jobs). Same code, different mode.

Why the worker is separate: a job takes 20 minutes. If the API did that work itself, the website would freeze for everyone else.

CloudFront and WAF — the front door and the guard

Everything from the internet arrives here first.

CloudFront is Amazon's delivery network. It has machines in many countries; a visitor connects to a nearby one instead of crossing the world to Mumbai. It also provides the padlock in the browser — the HTTPS encryption — and remembers unchanging things like your logo so they load instantly.

WAF stands for Web Application Firewall. It is the guard reading requests before they reach us, and it does two useful jobs:

  • Blocks well-known attacks. Amazon maintains rule sets for the standard techniques people try on every website in the world. We switch them on rather than inventing our own.
  • Rate limiting. If one address sends 10,000 requests a minute, it is blocked before our code wakes up. This is what stops someone guessing passwords all night, and what stops a flood knocking the site over.

Why it matters that this is first: attacks that never reach your program cannot exploit a bug in your program.

Terraform — the floor plan

A written description of every piece of AWS we use.

The problem it solves. Normally you build cloud infrastructure by clicking around a website: create a database, tick some boxes, set a password, create a bucket, adjust a setting. Six months later nobody remembers what was ticked. Rebuilding it elsewhere means rediscovering every choice, and the one setting you forget is usually a security one.

What Terraform does. You write the description in files instead:

resource "aws_db_instance" "main" {
  engine                  = "postgres"
  instance_class          = "db.t4g.micro"
  storage_encrypted       = true      # encrypted on disk
  publicly_accessible     = false     # not reachable from the internet
  backup_retention_period = 7         # a week of backups
  deletion_protection     = true      # cannot be deleted by accident
}

Then one command builds it. The files live in your private repository, so every decision is recorded, reviewable, and repeatable.

Why this is the answer to "easily movable to another AWS account". Moving becomes: run the same files against the new account with a different account number, then copy the data in. Without Terraform, moving means weeks of clicking and hoping you matched every setting. This single choice is what makes your migration requirement realistic rather than aspirational.

Secrets Manager — the safe

Where every password and key lives.

The thing to avoid. Keys written into code, or into a settings file, end up in the code repository, in someone's laptop backup, in a screenshot. This is how keys leak — almost never by clever hacking.

How it works instead. The key is stored in Secrets Manager. Our program is given an identity by AWS — not a password, an identity — and that identity is permitted to read one specific secret. When the program starts, it asks for it. The key exists in the program's memory and nowhere else.

What goes in it:

  • The database password
  • The payment provider's keys
  • Your GPU box's keys — the Hugging Face token, the Google service account, the Gemini proxy key. Right now the Hugging Face token sits in the container's environment, where it shows up in diagnostics. It should be rotated once and delivered from the safe from then on.

What the browser gets: none of it. Ever. The website sends the visitor exactly three things — their own session cookie, their own data, and 15-minute file links.

EventBridge and Lambda — the caretaker who turns the machine off

The piece that saves you money while you sleep.

Lambda runs a small piece of code without any server, only when called, and costs essentially nothing at this scale. EventBridge is the alarm clock that calls it — here, once a minute.

What it checks, every minute:

Is any job being worked on right now?      -> if yes, do nothing
Is any job waiting in the queue?            -> if yes, do nothing
Did the last job finish over 5 minutes ago? -> if yes, and the GPU is on:
                                               turn it off

Why it lives outside the main program. If the API crashes or is restarted, the caretaker keeps working. The expensive machine is never left running because something else failed.

Why it asks the database and not the machine. A GPU that is loading a model looks idle. The database knows the truth: there is a job with the state "processing". Guessing from how busy the machine looks would eventually kill somebody's job halfway through.

The rule I would defend hardest in the whole design: if the caretaker cannot reach the database, it does nothing and raises an alarm. Leaving the machine on wastes about 50 cents an hour. Turning it off during a render destroys 20 minutes of a paying customer's work. So the failure is deliberately the expensive one.

3. How they work together: following one video

One person, one video, from arriving at the site to downloading the dub. At every step I name which piece is working and, where it matters, what is deliberately not happening.

Step 1 — Signing up

Browser  --> CloudFront/WAF --> FastAPI --> PostgreSQL
                                        --> SES (email)
  • The visitor types an email and password. It travels encrypted.
  • WAF checks this address is not flooding us.
  • FastAPI scrambles the password with Argon2id — a deliberately slow, memory-hungry one-way scrambler. Slow is the point: it makes guessing millions of passwords impractical even if the database is stolen. It cannot be reversed, so nobody, including you, can ever read anyone's password.
  • PostgreSQL stores the user as "not yet verified".
  • SES emails a link that works once and expires in 24 hours.

Deliberately not happening: the reply does not say whether that email already had an account. Otherwise the signup form becomes a tool for discovering who your customers are.

Step 2 — Logging in, and what a cookie really is

Browser  --> FastAPI --> PostgreSQL
Browser  <-- cookie

A cookie is a small note the server asks your browser to keep and show again on every later visit — like a cloakroom ticket. Ours contains a long random number and nothing else. It carries no name, no email, no plan.

Three properties, and each one blocks a specific attack:

PropertyPlain meaningWhat it stops
HttpOnlyCode running in the page cannot read the cookieIf an attacker ever manages to inject a script into the page, it still cannot steal the login
SecureOnly ever sent over an encrypted connectionSomeone watching public wifi cannot copy it
SameSiteNot sent when another website triggers the requestA malicious page cannot make your browser perform actions as you

And in the database we store only a fingerprint of the ticket, not the ticket. If someone stole the entire database they still could not log in as anybody. Deleting the row logs that device out instantly — which is why we use this design rather than the popular alternative that cannot be revoked.

Step 3 — Uploading the video

Browser  --> FastAPI            "may I upload?"
FastAPI  --> PostgreSQL         checks plan and minutes left
FastAPI  --> Browser            a 15-minute write link
Browser  --> S3                 THE VIDEO GOES HERE, DIRECTLY
Browser  --> FastAPI            "done, here is the id"
FastAPI  --> ffprobe            what is this file really?
FastAPI  --> PostgreSQL         create the job, state = queued
  • The API checks quota before the upload, so nobody waits ten minutes to be told no.
  • The video never passes through our API. That keeps the API small and cheap.
  • ffprobe is a tool that opens the file and reports what it truly is. We use it because a filename is a claim, not a fact — anyone can rename anything to .mp4. We check the real duration and format, and bill on the real duration.
  • The stored filename is one we generate. The visitor's own filename is kept only as a label to show them, never used as a location on disk — using it would be one of the classic ways attackers reach files they should not.

Step 4 — The GPU wakes up

FastAPI  --> PostgreSQL   "is the GPU already on?"
FastAPI  --> AWS EC2      StartInstances
Worker   --> GPU box      "are you ready yet?" (polling)
  • If it is already running, nothing happens — the job simply queues behind the current one.
  • If not, it is started. About two minutes to boot, plus about a minute to load the voice model. The visitor sees an honest message rather than a spinner that pretends.
  • The decision is made while the relevant database row is locked, so two people uploading at the same instant cannot start two machines.

Step 5 — The dubbing, which is the part we do not touch

Worker --> S3         fetch the video
Worker --> GPU box    upload, transcribe, translate, generate, export
Worker --> PostgreSQL store progress, and store the transcript + translation
Worker --> S3         put the finished dub back

The worker takes one job at a time — there is one GPU, so two jobs at once would only make both slower. It calls the same VoiceStudio steps your browser calls, in the same order, with the same settings.

The one genuinely new thing. Today the translated text lives in your browser — that is why refreshing the page loses it. A server cannot depend on a browser, so the worker keeps the transcript and translation in PostgreSQL between the translate step and the render step, then hands the identical text back. We store what the engine gives us and return it unchanged. This is bookkeeping around the engine, not a change to how it dubs.

Step 6 — Getting the result

Browser --> FastAPI      "is job 12345 done?"
FastAPI --> PostgreSQL   look it up, but only if it belongs to this user
Browser --> FastAPI      "give me the file"
FastAPI --> Browser      a 15-minute read link
Browser --> S3           download

Every lookup is written so that ownership is part of the question, not an afterthought:

SELECT * FROM jobs WHERE id = :job_id AND user_id = :the_logged_in_user

Not "fetch the job, then check who owns it" — because one forgotten check in that style is how people end up seeing strangers' videos. And if the job is not yours, the answer is "not found" rather than "not allowed", so the API will not even confirm that someone else's job exists.

Step 7 — Five minutes later, the machine turns itself off

EventBridge --> Lambda --> PostgreSQL   "anything running? anything waiting?"
Lambda      --> AWS EC2                 StopInstances

Nothing running, nothing queued, five quiet minutes: off. A quiet day costs you the fixed monthly charges and not one rupee of GPU time.

A pleasant side effect: because it waits for the queue to be empty too, a burst of uploads is handled back-to-back on one boot. That is both faster for users and cheaper per video than starting and stopping repeatedly — worth remembering when you set prices.

If you are used to MongoDB Atlas, here is the translation:

Opening users looks like this:

You can sort, filter, search and click into any row, exactly as in Atlas. You can also ask questions across several tables at once, which is where a relational database earns its place:

-- everyone who signed up but never confirmed their email
SELECT email, created_at FROM users WHERE email_verified_at IS NULL;

-- this week's failed jobs, with who they belonged to and why they failed
SELECT j.id, u.email, j.error_code, j.finished_at
FROM jobs j JOIN users u ON u.id = j.user_id
WHERE j.state = 'failed' AND j.finished_at > now() - interval '7 days';

4.2 The honest difference from Atlas

Atlas gives you a data browser hosted by MongoDB — you log into their website and look at your data. AWS does not provide that for PostgreSQL. The AWS console shows the database's health, size and settings, but not its rows. So the browsing screen comes from a free tool you run on your own laptop instead. Same result, different place.
OptionHow it feelsSecurityMy view
DBeaver or pgAdmin on your laptop, connected through a secure AWS tunnelA desktop app with the familiar grid of rowsBest. The database stays private, nothing is exposed to the internet, and every connection is recorded by AWSRecommended. Free, about ten minutes to set up
A web tool such as pgweb or Metabase, hosted by usClosest to Atlas — open a web addressWeaker: it is a login page standing in front of your database, and it becomes something else to secure and patchOnly if the browser feel really matters to you
Use Aurora instead of plain RDSAWS's own query editor, in the consoleGood, fully AWS-nativePossible, but Aurora costs more, and I would want to confirm current support before committing

The tunnel is two steps. One command opens a private, authenticated pipe:

aws ssm start-session --target <instance> \
  --document-name AWS-StartPortForwardingSessionToRemoteHost \
  --parameters '{"host":["<database-address>"],"portNumber":["5432"],
                 "localPortNumber":["5432"]}'

Then you point DBeaver at localhost:5432 and it behaves like a database on your own machine. No SSH key to lose, no public database, and AWS records who connected and when.

4.3 The folders you can browse: S3

The videos are not in the database — they are in S3, and that is a folder-style browser, built into the AWS console, with no extra tool:

s3://dubbing-prod-media/
+-- uploads/{user_id}/{upload_id}.mp4    source videos, deleted after 7 days
+-- outputs/{user_id}/{job_id}.mp4       finished dubs, deleted after 30 days

Click through the folders, preview, download. Each user's files sit under their own id, which makes "delete everything belonging to this person" a single, reliable operation.

4.4 Two logins for you, not one

I would give you two database accounts:
  • A read-only one for everyday looking, so you cannot change production by accident while browsing.
  • An admin one you reach for deliberately when you genuinely need to change something.
And a support view — a saved query that shows what you need and hides what you do not: 
CREATE VIEW support_users AS
SELECT id, email, status, role, email_verified_at, created_at
FROM users;        -- the scrambled password is deliberately absent
You will never see anyone's password in any case — they are one-way scrambled. But there is no reason for that column to be on your screen during routine support either.

5. How each piece is protected

One row per piece, so you can see there is a specific defence rather than a general hope.

PieceThe worryWhat protects it
PasswordsDatabase stolen, passwords crackedArgon2id one-way scrambling, deliberately slow and memory-hungry. Cannot be reversed. Changing a password logs out every device.
Login sessionsSomeone steals a loginOnly a fingerprint of the ticket is stored, so a stolen database yields no working logins. The cookie is unreadable by page code, encrypted-only, and not sent from other sites.
One user seeing another's videosThe classic serious leakOwnership is part of every database question, not a separate check. Unguessable random ids. "Not found" rather than "not allowed", so nothing is confirmed.
The APIBad input, floods, guessingWAF and rate limits at the door; FastAPI validates every field; login lockout with backoff; no endpoint accepts a URL or file path from the client.
The databaseDirect attack from the internetNo public address at all. Only our own programs may connect. Encrypted on disk, encrypted in transit, backed up with point-in-time recovery, protected against accidental deletion.
The videosSomeone finds a public linkThe bucket is fully private. Access only ever by a 15-minute link tied to one file. Encrypted at rest. Old files deleted automatically.
Keys and passwordsLeaking through code or gitAll in Secrets Manager, fetched by identity at startup. Nothing in code, nothing in the repository, nothing sent to the browser. Automated scanning blocks a key being committed by mistake.
Your GPU boxIt has no password of its ownNo public address. Its door opens only to our worker, identified by AWS's own grouping — not by an IP address, and not to the internet. Fine today because your firewall allows one home address; a public website makes this essential.
PaymentsFake "I paid" claims; card dataCard details are entered on the payment company's own page and never touch us. Upgrades happen only when a signed message from the provider arrives. Each message is recorded once, so a replayed one does nothing.
DeploymentsStolen AWS keys from the build systemThere are no stored AWS keys. The build system borrows a short-lived identity for each run.
UploadsDisguised or oversized filesChecked with ffprobe after upload, not trusted by name. Size and length capped by plan. Stored under a name we generate, never the visitor's.
LogsSecrets leaking into logsPasswords, tickets, reset links and file links are never written to logs. User ids are logged rather than email addresses.
The single sentence version: the visitor's browser holds one meaningless random ticket and receives short-lived links to its own files. Everything else — every key, every password, all the logic, all the data — stays on the server side, and the expensive machine that does the dubbing has no door to the internet at all.

7. A simpler version, if you want to start smaller

I recommended Fargate, but I should be straight with you: for a first launch you could run the whole API on one small ordinary server and save roughly $15 a month.

One small server (EC2 + Docker Compose)Fargate (recommended)
Costabout $12/monthabout $18–30/month
SetupSimpler to picture: one machine you log intoSlightly more to learn up front
Security updatesYour job, foreverAmazon's job
If it breaks at 2amYou log in and fix itIt is replaced automatically
GrowingBuy a bigger machine and move everythingChange one number
Migrating accountsSame either way — Terraform describes bothSame

My honest view: the $15 saving is real but small, and the thing you are buying is not having a server to forget about. An unpatched server is one of the most common ways small companies get broken into, and the risk grows quietly with every month nobody looks at it. Since you are handling other people's videos and card-adjacent data, I would spend the $15.

What I would not compromise on regardless of which you choose: Postgres on RDS rather than a database you run yourself, S3 rather than server disks, Secrets Manager rather than configuration files, Terraform rather than clicking, and the GPU box kept off the internet. Those five are what make the difference between a system that is safe and one that merely has not been attacked yet.

If you remember five things from this document.
  1. The dubbing engine is untouched. Everything here sits around it and talks to it the way your browser already does.
  2. The visitor's browser holds one random ticket and nothing else. Every key stays on the server.
  3. The GPU turns itself on for work and off after five idle minutes — and the caretaker will never turn it off while a job is running.
  4. Because the whole setup is written down as files, moving to another AWS account is a repeatable procedure rather than a rebuild.
  5. You can browse your data any time with a free desktop tool through a private, logged tunnel; your files you can browse in the AWS console directly.
